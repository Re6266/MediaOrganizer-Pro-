# MediaOrganizer-Pro 项目周报

**周报周期：2026年10月26日—2026年11月1日**

## 一、本周工作进展

本周主要围绕项目初期开发工作展开，在前期选题和需求讨论的基础上，开始搭建项目基础框架，并完成数据库设计及 GitHub 代码仓库配置。

1. **项目基础框架搭建**：使用 Python 和 Streamlit 搭建项目基础运行环境，完成项目目录结构及相关配置文件的初步设计，实现了基础页面的创建与运行。

2. **数据库设计与实现**：采用 SQLite 作为本地数据库，设计并创建媒体文件、照片分组、分组合成任务、合成来源记录和操作日志等数据表，为后续媒体索引、照片分组及 AI 合成功能提供数据存储基础。同时完成了数据库连接、数据插入和查询等基础操作，并进行了初步测试。

3. **数据库结构完善**：结合项目后续功能规划，对数据库结构进行了扩展，增加了 AI 合成任务及来源照片记录等相关字段和数据表，为后续功能开发预留接口。

4. **代码仓库配置**：完成 Git 和 GitHub 的基础配置，建立小组项目远程仓库，将本地项目代码与远程仓库进行合并同步，实现了项目代码的首次集中上传，为后续组内协作和版本管理做好准备。

5. **项目设计文档整理**：初步整理了系统整体架构和数据库 E-R 关系，为后续项目报告撰写及功能模块开发提供参考。

## 二、当前存在的问题与障碍

1. 目前项目主要完成基础框架和数据库部分，媒体文件扫描、元数据提取、重复文件检测等核心业务功能尚未正式实现。
2. AI 最佳瞬间合成功能涉及图像分析、特征提取和图像生成等技术，具体实现方案及技术可行性仍需进一步研究。
3. 小组成员对各模块的开发接口和数据交互方式还需要进一步明确，以降低后续模块集成时出现冲突的可能性。
4. GitHub 远程仓库配置过程中遇到了网络连接及本地与远程提交历史不一致的问题，目前已通过代理配置和合并远程分支解决。

## 三、本周关键决策及理由

1. **确定采用 Python + Streamlit + SQLite 作为项目初期技术方案。** Python 具有较丰富的图像处理和 AI 相关库，Streamlit 能够快速搭建可交互的 Web 页面，SQLite 则适合本地数据存储，整体技术门槛和开发成本较为适合当前团队。

2. **采用本地数据库管理媒体索引信息。** 原始图片和视频仍保存在用户指定目录中，数据库主要保存文件路径、基本属性及相关管理信息，避免直接修改原始媒体文件。

3. **增加 AI 合成任务及来源记录的数据结构。** 考虑到后续需要支持自动分析和用户手动选择两种合成模式，因此提前设计相关数据表，为功能扩展做好准备。

4. **采用 GitHub 进行代码版本管理。** 通过远程仓库统一管理项目代码，保留各成员的提交记录，方便后续协作开发、代码回溯和项目验收。

5. **对 AI 辅助产出进行筛选和调整。** 本周主要将 AI 辅助用于技术方案讨论、数据库结构设计及代码完善。对于 AI 提出的设计建议，结合项目实际需求和团队开发能力进行判断，优先采用能够落地、便于测试且不会破坏原始媒体文件的方案，而不是直接照搬复杂的技术方案。

## 四、下周工作计划

1. 开始实现本地图片和视频扫描功能，支持用户选择指定目录并遍历其中的媒体文件。
2. 完成图片和视频基础元数据提取，包括文件类型、大小、分辨率、拍摄时间等信息。
3. 将扫描结果写入 SQLite 数据库，实现媒体文件的初步索引和展示。
4. 对扫描功能进行测试，重点检查不同文件格式、异常文件和重复扫描等情况。
5. 进一步明确各模块之间的数据接口和开发规范，推动小组成员按照分工开展后续开发工作。

**本周总结：**

本周完成了项目从前期方案讨论向实际开发的初步过渡，搭建了基础运行框架，完成了数据库的初步设计与测试，并建立了 GitHub 远程代码仓库。下一阶段将重点推进本地媒体扫描和元数据提取功能，逐步完善项目的核心业务流程。
